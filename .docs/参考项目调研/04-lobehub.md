# LobeHub 源码调研

核对对象为 `.upstream/lobehub` 的 `canary` 提交 `d86a85bcea15a5e1c3131f1d69bb1c08769a8819`，提交日期 2026-11-19。以下结论来自执行入口、持久层和测试源码；部署开关、托管环境能力和外部 API 的实测结果有待另行验证。README 用于发现功能入口。 [源码快照](https://github.com/lobehub/lobehub/tree/d86a85bcea15a5e1c3131f1d69bb1c08769a8819)

最适合 Muster 借鉴的是任务、会话、运行各自建模，接收和完成分别确认，终态与业务验收分开，用户从任务卡进入证据和请示。LobeHub 为跨运行时统一呈现投入了专用驱动、事件转换、网关和消息持久化。Muster 首版用 CLI 配置档和少量生命周期事件即可保留上述产品能力。

| 内置助理及配置 | `AgentRuntimeService` 创建 operation，执行 step，处理工具调用与恢复。另有内置助理、系统 Agent、模型供应商和 workspace/private 资源访问。团队协作另有 `GroupOrchestrationRuntime`/`Supervisor`，可根据主管决策调用单个或并行调用成员，属于 LobeHub 内部模型和工具循环。 | 只参考规划者和执行控制服务分工。中心 dsh 决策与汇报，中心服务持有任务事实、调度及验收，设备上的原生 agent 自主完成任务。团队协作用同一个任务树表达。 |

## 3. 状态、调度、接续和结果回调

1. **共同启动入口。** 手动、定时、依赖解锁、Goal 执行汇合到 `TaskRunnerService.runTask`。它检查并发 Topic，处理超时关联，条件更新任务为 running，校对设备目录，选择新/旧 Topic 和上下文后才调用执行服务。已受理与未受理分别处理，取消/收回在启动中发生时取消已出现的 operation。抢占时假定任务状态及 Topic 配置会变化，更新前比较读到的状态；执行拒绝时只在新值仍是本轮写入的情况下回滚。
2. **父子关系、依赖和验收。** 数据库单独存任务、依赖边、Topic 关联、活动、评论、文档和 Brief；任务服务执行状态变更和完成后的依赖传播。`onTopicComplete` 用 Redis 租约保护结算、失败时允许重试。`TaskLifecycleService` 两次核对是否已被更新的 operation 取代，handoff 摘要失败时保存原输出，普通子任务可独立完成以解锁下游，已确认 Verify 的任务把接受与回调交给 Verify。本次代码中的 `packages/business-server/src/task/onTaskRunCompleted.ts` 是空桩。无 Redis 的 HTTP handler 允许照常结算，无法提供同等去重保证。 [任务生命周期](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/taskLifecycle/index.ts#L134)
3. **定期调度与恢复分开。** `scheduleDispatch` 按 cron、时区和 last-run 查到期 occurrence，队列模式可以提前预约分钟内的下一次发生项，QStash 模式给每个任务独立重试预算。`heartbeatTick` 服务自动任务的周期触发；`watchdog` 检查 heartbeat 超时、孤立运行，以及重置卡住的 creator callback；`StaleOperationReaper` 则核对 operation lease，在原运行状态仍可恢复时补排步骤，在失效条件成立时收尾。定时 heartbeat 与设备 presence 具有不同语义。
4. **结果送达。** `onCreatorComplete` 检查之前是否送达，保留发送到平台的分片进度，外部发送失败返回可重试错误，送达成功后才结算回执。对于某些事件，任务消息、结果回调可转换为父会话模型需要的上下文。Muster 可以用同库的 outbox 记录回调，请示和根任务终态各配稳定业务键。报错展示使用已入库的事实，不依赖中心 dsh 摘要成功。
5. **实时订阅。** Agent gateway 协议区分运行 ID、订阅游标与 `resume_complete`；`GatewayMuxClient` 将 gap 和终态提供给上层，Web 对话在有 gap 时触发数据库重拉。Web 对话恢复和设备的 CLI 恢复分别有状态。Muster 在 PostgreSQL 保存按提交顺序分配的事件游标。Web 用 SSE 从快照或上次游标补读，游标过期时重取快照，设备协议另行处理待发回执。 [Web 对话恢复代码](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/src/store/chat/slices/agentRun/actions/transports/gateway/gateway.ts#L641)
6. **Goal 图和监督器。** `GoalManagerService` 记录已认领的计划/活动轮，用 `scheduleGoalAdvance` 推进；`GoalSupervisorService` 对图节点失败做限额和预算检查，按状态 claim 后在原任务范围安排恢复，并保留事故和对应 operation 关联。对于单人自动修 bug，Muster 用小规模父子依赖、重试预算和独立验证足以覆盖，Goal 计划器、图监控与自动诊断可后置。

## 4. GitHub、独立 Review 和验收

1. **Task Review 是评分服务。** `TaskReviewService.review` 获取 judge 模型/供应商，按 rubrics 评价待审文本，LLM 类型规则走 `generateObject`，默认通过阈值为 0.6，汇总为 0–100 分。任务 Review API 可以改配置并发起显式 Review。当前 `TaskLifecycleService` 的自动结算已移除原有 rubric 自动评分，交付验证走下面的 Verify。
2. **Verify/Acceptance 是独立执行与证据结算。** `AcceptanceService` 分别使用 VerifyRun、CheckResult、Evidence、Report，能够将检查运行与验收关联并保留判定。`createVerifierAgentRunner` 为 agent 型检查开新 Topic，以 `parentOperationId` 关联原运行，附上交付、规则与证据，指定 `verifierAgentId` 时按该 Agent 自己的设备和供应商执行，缺省回退内置 Verify agent。验证者调用 `submitVerifyResult`，终态 hook 兜底未提交或执行错误的检查。`driveTaskFromVerify` 用 claim 防止回调重复推进，区分通过、未满足、执行错误和 Review 错误。任务详情把证据及检查状态与对话分隔。Muster 可借鉴独立检查绑定原运行、传入证据以及从验证结果驱动完成，具体到 Git 还需确保审查和推送使用同一已验证的 commit。 [独立验证 Agent](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/verify/agentVerifier.ts#L28)、[Verify 结算](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/verify/settle.ts#L132)
3. **SCM 接收真实外部事件。** GitHub App 接入将 webhook 的安装、仓库、PR、检查和 Review 事件正规化。`ScmIngestService` 决定绑定/作用域、保存变更和检查。`ScmControlService` 可在合并时更新 Work/验收，也可依据用户配置在 CI 失败、Review 评论或请求修改时唤醒关联 Topic。防抖、唤醒次数上限、草稿过滤、来源审核和路由权能限制，用来防止重复事件放大与错误唤醒。GitHub 上关联 PR/CI 的状态与模型答复来源不同，适合独立展示。
4. **Muster 首版修 bug 路径。** 修复者产出测试退出码、执行范围和待推送 commit。若启用独立 Review，调度另一个 agent 的独立运行，给它指定 commit、目标分支和约定检查项。Review 在固定快照上给出结论及证据，失败或修改 commit 回到执行，重新测试并按项目策略复审。通过后在执行设备按配置推送，记录真实远端/分支及确认结果，最后聚合到根任务汇报。首版可直接从 Git 及测试进程读证据，后续再添加 GitHub App 监听及 PR 驱动重跑。

### 8.4 三条可以沿代码走到底的链路

1. **改选设备后启动，途中又取消。** `resolveRunExecution` 解析目标与目录 → `runTask` 发给执行端 → 设备进程确认 spawn → 服务在事务内复查任务；如派发期间被取消，反向请求停掉已启动的 operation。测试分别覆盖「取消且确认停掉」与「未能确认停止」，后者保留原派发事实供核对。Muster 的「已派发」「设备已开跑」「设备确认停止」应能独立查到。 [目标解析](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/taskRunner/resolveRunExecution.ts) · [启动与撤销](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/taskRunner/index.ts#L463-L551) · [设备切换与停止测试](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/taskRunner/runTask.explicitDevice.test.ts#L250-L295)
2. **不同 agent 复核同一次交付。** 原运行结算 → 将提交的产物、验收项和证据交给新的验证 Topic → 指定审查 agent 沿自己的配置执行，回传判定 → 完成后的回调才可将可验收结果返给原话题。测试覆盖新 Topic 继承父任务范围、审查者独立选择模型以及文件证据传入。Muster 还要自行锁定实际测试、Review 和 push 所针对的 Git SHA。 [独立审查执行](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/verify/agentVerifier.ts) · [验证者选择、隔离与证据测试](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/verify/__tests__/agentVerifier.test.ts#L73-L237) · [验证与回调时机](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/taskLifecycle/onTopicComplete.test.ts#L508-L549)
3. **两份报告几乎同时返回。** `TaskResultBridgeService.deliver` 从 handoff 或原输出生成内容 → 以任务和完成 Topic 构造稳定消息 ID → 按创建者会话加事务锁，在主线末尾追加 → 保存待唤醒记录并 drain。这样两个完成结果能轮流成为主线下一条，网络重送也能找到原消息。Muster 的 Go 中心使用 PostgreSQL 事务登记交付与待汇报项，插件送入原主会话生成汇报，中心按唯一业务键将回复写入主对话。 [回写与待唤醒记录](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/services/taskResultBridge/index.ts#L118-L209) · [回调入口测试](https://github.com/lobehub/lobehub/blob/d86a85bcea15a5e1c3131f1d69bb1c08769a8819/apps/server/src/router-hono/workflows/task/handlers/onCreatorComplete.test.ts)

专题覆盖公开源码中能定位的各主要产品面，选取代表链路检查代码和测试断言。未逐个核读每个供应商模型、插件命令、平台版本和界面变体，也未运行托管功能、桌面客户端或渠道账号。
