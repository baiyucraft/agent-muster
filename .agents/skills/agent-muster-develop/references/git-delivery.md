# Git Review 与交付

单独 Review 时，以用户指定的工作区差异、暂存内容或提交为候选。准备交付时用对应流程固定候选。只读检查、代码修复、提交、推送和部署分别以用户授权为准。自动修复只触及获准的候选路径或 hunk。发现范围外问题时说明位置与影响。[提交](commit.md) · [推送](push.md)

## Review 候选

1. 记录基线与候选 tree，逐文件检查变更、相关入口及调用方。删除、重命名、二进制和生成物检查实际来源及归属。查看状态和错误转换、并发、重试、旧数据、资源释放、日志与凭据。代码注释和业务验证按变更选择。[开发规范](development.md)
2. 跨端契约、持久化、恢复逻辑或累计改动较大时，可请独立 reviewer 只读审查。提供固定基线、tree 或 SHA、候选清单和已有证据，明确用户改动的边界。取得最终结果并复核发现。reviewer 无法完成时由当前 agent 补足同一范围，记录覆盖和缺口。
3. 对发现记录位置、触发条件、可观察影响、最小修复与验证方式。按影响区分需要修复的交付缺陷、已知遗留、环境问题和证据缺口。实际缺陷优先在授权范围内修复，再核对候选。涉及不明确的行为取舍或额外范围时保留现场并报告。
4. 根据行为或维护入口的变化检查 OpenAPI、README、Wiki、配置示例和相关 Skill。记录受影响材料的同步结果。工作区里的文档修订需要进入候选后，才能成为交付证据。

若已有 CodeGraph 索引，先用它查入口和调用链。索引与候选 tree 不一致时，将查询结果作为定位线索，从 index、提交内容或隔离 checkout 核实实现。

## 修复与验证证据

- Go 格式修复按明确文件执行 `gofmt -w`。JS／TS 运行 `pnpm exec eslint --fix <文件...>`。工具修复可能触及无关 hunk 时，在隔离候选内执行，只纳入经 Review 的修改。注释语义、接口和错误处理问题由 agent 按实现修复。
- 记录命令、环境、退出结果和对应 tree 或 SHA。只有测试实际读取同一候选，结果才归该候选。未暂存修改或未跟踪文件可能影响验证时，使用隔离快照和对应的依赖。相同 tree、环境和命令的有效结果可复用。候选或上下文变化后补查受影响部分。
- 检查候选的空白差异、最新的 Git 状态和授权范围。报告最终 Review、验证、未覆盖场景，以及实际提交或推送结果。调试日志、临时验证记录和一次性审查结果放在 `.tmp/`。[项目 Git 协作规范](../../../../.wiki/02-开发指南/02-Git协作流程.md)
