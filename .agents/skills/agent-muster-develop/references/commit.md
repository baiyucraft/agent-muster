# 提交前

1. 核对 `git status --short --branch`、HEAD、`git diff --cached`、`git diff` 与未跟踪文件。区分已暂存、未暂存、未跟踪和部分暂存。初始提交按无 HEAD 处理。说明本次目的、拟纳入的路径或 hunk 和排除项，确保实现、验证、依赖和契约变更组成可独立审查的提交。
2. 只有提交范围获授权时才暂存，以 `git add -- <明确路径>` 或批准的 hunk 操作。读取 index 与工作区的两层变化。原 index 有无关暂存时保留原内容，以隔离候选或独立 worktree 完成本次提交。完整路径的工作区内容都已审查并获授权时，才考虑 `git commit --only -- <路径>`。只批准部分 hunk 的路径使用隔离的已批准内容。
3. 执行 `git diff --cached --check`，用 `git write-tree` 固定非空候选，并读取完整暂存 diff。按共用流程审查、修复和验证。变更候选后重新固定 tree，并检查受影响差异及验证。确认 HEAD、候选和用户暂存内容符合本次操作预期。[共用 Review 流程](git-delivery.md)
4. 普通提交使用 `<type>: 【<模块>-<子模块>】<中文动宾摘要>`，模块路径来自实际职责。一个目的涉及多个模块时可连写模块块。正文按需记录原因、兼容边界和实际验证。

示例提交标题为 `fix: 【设备端-任务续接】防止重复处理子任务回执`。

仅准备或检查时报告候选、标题和验证结果。实际提交授权明确且必要检查完成后创建普通提交，核对 `git show --stat --oneline -1`、`HEAD^{tree}` 和工作区状态，确认提交内容与已审 tree 一致。如果用隔离 index 提交推进了当前 HEAD，对照新 HEAD 校对原 index，只更新已纳入提交的内容，并核验无关暂存条目和同文件未暂存 hunk 仍在。记录提交 SHA。提交失败时按实际原因处理并保留现场。
